# Постоянный журнал событий (v0.1.2)

Администратор: Журнал → фильтры/поиск/даты → подробности. Время хранится в UTC;
для показа доступны локальный часовой пояс, UTC и Europe/Moscow. Ввод границ дат
использует локальное время браузера. API `/api/journal` требует admin session,
возвращает максимум 200 записей; UI запрашивает 50, newest-first, с курсором
(last_at,id), без загрузки всей истории. Обновление раз в 10 секунд только на
открытой видимой первой странице; при уходе запрос отменяется.

Данные: `/data/state/events.db`, отдельная от очереди/сессий SQLite, права 0600.
Поля: UTC timestamp/first occurrence, severity, category, фиксированные event type
и описание, component, hashed correlation ID, direction, attempt, safe error class,
result и occurrence count. Текст сообщений, имена/ID адресатов, URI, секреты и raw
tracebacks не принимаются интерфейсом записи. Каталог разрешённых событий находится
в `shmax/journal.py`; произвольные строки/поля не сохраняются.

По умолчанию: 90 дней, 100 000 записей, бюджет 128 MiB. SQLite использует DELETE
journal, WAL/SHM не создаются. `max_page_count` ограничивает основную БД примерно
половиной бюджета за вычетом резерва 1 MiB (минимум 64 KiB при меньших бюджетах); вторая половина резервируется под rollback
journal. Индексы входят в размер БД. UI учитывает максимум логического и выделенного
размера файлов events.db, -journal, -wal, -shm. Это консервативный бюджет SQLite
файлов, не filesystem quota и не обещание точного предела для метаданных самой ФС.
Сторонние процессы/ручное изменение БД находятся вне этого ограничения.

Проверка age/count/size выполняется пакетами; удаляется до 1000 старых записей за
транзакцию, затем incremental_vacuum до 256 страниц. В простое обслуживание идёт
раз в минуту, поэтому age cleanup выполняется постепенно. Свободные SQLite pages
переиспользуются; освобождение места ОС также постепенное. Полного VACUUM на пути
доставки нет. Очередь RAM — 1024 metadata events, batch — до 128. I/O в worker thread,
производитель не ждёт диск. При заполнении/ошибке записи события могут быть пропущены:
счётчики dropped/write_failures показаны в UI. Доставка сообщений продолжается.
Это диагностический журнал, не гарантированная финансовая/audit запись.

Одинаковые network failures агрегируются по компоненту, типу, классу и эпизоду;
recovery завершает эпизод. После restart начинается новый сегмент. Успехи разных
сообщений не агрегируются. correlation ID связывает received/queued/delivery события;
у существующих до обновления queue rows используется q-ID. Успех доставки появляется
после API acknowledgement, записи mapping и durable queue acknowledgement.

Файлы журнала переживают restart/update в существующем state volume. Обычный backup
снимает events.db через SQLite backup API; portable backup уже snapshot-ит SQLite.
Retention никогда не затрагивает другие persistent data. Ранее завершённые ошибкой доставки разбираются отдельно; автоматического replay нет.

## Ошибка обработки до очереди — v0.1.3

`message.processing_failed` — ERROR с направлением и correlation ID. Это ошибка обработки входящего события; запись доставки в очереди могла ещё не появиться. Текст исключения и содержимое сообщения не сохраняются. Отдельное Telegram-уведомление не отправляется.
