# Восстановление и перенос SHMAX

## Перенос на свежий сервер

1. На старом сервере создайте [зашифрованный экспорт](backups.md) и сохраните один файл .shmax и пароль отдельно.
2. Остановите старый SHMAX. Не запускайте два экземпляра с одним Telegram Bot/MAX аккаунтом одновременно; перенос не отзывает исходные credentials.
3. Установите SHMAX на новом Debian-хосте и создайте нового владельца обычной setup-ссылкой.
4. На экране «Как настроить SHMAX?» выберите «Восстановить из резервной копии». MAX, Telegram и остальные шаги ещё не нужны.
5. Выберите файл, введите пароль и нажмите «Проверить резервную копию». Просмотрите дату, версию, состав и предупреждения. До подтверждения данные не меняются.
6. Подтвердите остановку старого экземпляра и нажмите «Восстановить SHMAX».
7. После перезапуска войдите **с логином и паролем нового владельца**. Откроется dashboard; шаги 2–10 повторять не требуется. Проверьте маршруты, ACL, подписи и обе стороны моста, затем перезагрузку.

Новый владелец остаётся единственным веб-владельцем независимо от совпадения ID/username в импортированной БД. Старые веб-администраторы, setup-токены и веб-сеансы удаляются, ключ подписи cookie обновляется. Telegram-пользователи, их роли/одобрения/блокировки и локальные подписи сохраняются. Неизвестные участники не одобряются автоматически.

Завершённые доставки, idempotency keys и reply/native-ID mappings сохраняются. Незавершённые pending/retry/processing записи переводятся в failed с `migration_review_required`: проверьте их вручную перед повтором, поскольку исходный сервер мог успеть отправить сообщение. Media cache не переносится.

## Проверки и откат

Аутентификация администратора, CSRF, роль владельца, ограничение размера и rate limits обязательны на сервере. Весь файл расшифровывается/аутентифицируется до распаковки в отдельный staging. Проверяются внутренний манифест, SHA256/размеры, пути, типы записей, master key, SQLite integrity и известная Alembic revision. Симлинки, hardlinks, traversal, special files и распаковочные бомбы запрещены. Более новая версия приложения/неизвестная схема отклоняются; известная прежняя схема мигрирует вперёд. Отката схемы назад нет.

Hostd получает только случайный ID операции, не произвольную команду/путь/пароль. Он повторно проверяет содержимое, мигрирует staging, останавливает web-контейнер, сохраняет прежние постоянные каталоги, подставляет восстановленное состояние с правильным UID/GID, запускает контейнер и проверяет host-side `/health/ready`. Docker socket в web не появляется. Журнал фиксирует каждый обмен каталогов; при сбое выполняется откат. При прерывании hostd незавершённый обмен откатывается при его следующем старте.

Ошибка пароля/повреждение: «Неверный пароль или повреждённая резервная копия». Текущие данные не меняются. Если неудачен restart/readiness, возвращается прежнее состояние. Если неудачен и откат, статус `rollback_failed` явно требует помощи владельца; не удаляйте /var/lib/shmax, сохраните `previous/` и журнал.

## Сеансы и новый IP

Новый deployment bind/IP, порт, окружение и аппаратные binaries остаются настройками нового сервера. Telegram/Xray восстанавливаются из конфигурации/SecretStore; MAX использует доступный сохранённый сеанс. Внешние службы вправе отозвать сеанс: выполняйте адресную повторную авторизацию только этой интеграции. Telegram, маршруты, пользователи и секреты других интеграций не удаляются. Общее `/health/ready` проверяет работоспособность БД/хранилища; затем владелец проверяет реальную доставку обеих интеграций.

## Старые локальные копии

CLI `shmax restore <архив>` — низкоуровневая локальная распаковка: сначала самостоятельно сделайте safety-копию и остановите приложение; CLI не предоставляет новый portable onboarding/hostd transaction. Старый in-process API восстановления заблокирован в production (HTTP 409). В v0.2.0 тот же интерфейс владельца принимает переносимые v2 и старые локальные v1: `.shmax`, `.shmax.enc` и штатный gzip-tar с манифестом. Старые копии проверяются и преобразуются во временной области до штатной hostd-транзакции. Для зашифрованной v1 принимается исходный пароль от 8 символов; для незашифрованной оставьте поле пустым. Формат определяется содержимым, а не расширением. Сеансы, маршруты, Telegram-пользователи и их права мигрируют; новый владелец и правила запрета автоматического повтора очереди сохраняются. Копия без ключа SecretStore или с повреждённой базой не может быть восстановлена; текущие данные остаются нетронутыми.

Служебные cold snapshots updater без манифеста приложения — отдельный формат локального отката, а не пользовательский переносимый файл. Для них используйте штатный путь восстановления updater/владельца на остановленной системе.

Безопасная диагностика на Debian:

```sh
systemctl status shmax-hostd.service shmax-boot.service
journalctl -u shmax-hostd.service --since '-10 minutes' --no-pager
stat -c '%u:%g:%a' /run/shmax/hostd.sock
```

Не публикуйте резервную копию, пароли, токены, URL подписок, API Hash или ключ SecretStore.
