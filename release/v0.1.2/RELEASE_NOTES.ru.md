# SHMAX v0.1.2 — восстановление соединений и журнал событий

Кандидат патч-релиза. Публикация и установка требуют отдельного решения владельца.

- Исправлена ошибка TransportConfig при смене Xray. Проверяется полный путь с bot token; переключения сериализованы с Telegram recovery. Ответ различает применение сети, установку адаптера и rollback. При неудаче выполняется попытка вернуть предыдущий работающий узел. Прямого fallback нет.
- MAX автоматически восстанавливает временные сетевые разрывы через сохранённую сессию: один владелец lifecycle, ограниченные timeout, backoff с jitter. SMS и автоматический logout/relogin не запускаются. Отозванная сессия требует вмешательства оператора.
- При reconnect останавливается старый MAX listener и создаётся один consumer текущего поколения; устаревшие SDK callbacks игнорируются. Health учитывает listener, временная невозможность проверки отличается от AUTH_REQUIRED.
- Добавлен постоянный приватный журнал операций в Web UI: фильтры, поиск, cursor pagination, подробности и обновление каждые 10 секунд при открытой видимой странице. Только метаданные, без текстов сообщений и секретов.
- Журнал ограничен возрастом 90 дней, 100 000 записей и бюджетом 128 MiB; отдельная SQLite, bounded queue, пакетная запись вне event loop, постепенная очистка. Повторные сетевые ошибки агрегируются; успешные доставки остаются отдельными.
- Xray stderr постоянно считывается; сохраняются только безопасные категории.
- Пустые outbound payload и постоянные Telegram 400/401/403 не повторяются с тем же некорректным запросом. Старые failed-записи не изменяются автоматически.

Сохранены фотоальбомы v0.1.1, ID aliases, checkpointing, replies/topics, ACL, chat_id=0 и зашифрованные сессии. Семь исторических MAX media errors не имеют доказанной общей причины; этот релиз не заявляет их ретроспективного исправления.

Обновление: сначала проверить подписанный архив и резервную копию, затем использовать штатный `sudo shmax update /path/to/shmax-v0.1.2.tar.gz`. Обычный переход с v0.1.1 не требует повторной авторизации. Конфигурационный backup не заменяет холодную копию всех persistent data, которую создаёт штатный updater. При failed readiness updater возвращает прежний образ и холодные данные. Не применять на production до одобрения.
